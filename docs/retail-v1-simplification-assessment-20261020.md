# 散戶 v1 最小交易流程：精簡評估

日期：2026-10-20。狀態：**靜態評估與 R1 政策定案完成；後續 R1 local-sim 已實作、自測 197／197 通過，待獨驗，未啟用交易。** 詳見[R1 交付](risk-period-r1-local-sim.md)；第 7 節前次文件檢查保留為歷史證據。

使用者核准以 1,000～10,000 USDT、個人本機、單人維護重新評估複雜度，並於同日後續明確同意 R1 定案。第 5 節已取代相應舊基準政策；其他「建議」不自動變成已核准政策。本次定案不授權新採集、Demo／Live、DB 遷移或 Git 操作。前端並行工作繼續依原交辦範圍進行。

## 1. 結論與現況校正

應縮小首版必交範圍，讓一般異常能自動確認、讓使用者知道還能做什麼。單純以本金較小為由取消重複送單防護、未知委託追蹤或部位核實，不能解決操作負擔。

本次核對本地程式、契約及測試來源，確認：

1. **沒有「每次下單重播全部歷史」這個現行實作。** 對帳驗證指定採集窗口；`Supervisor.reconcile_report` 消費已取得的報告，本身不做 transport。`dispatch` 走既有意圖、風控與執行入口。訂單終結後仍需重新核實責任，不能因此宣稱未來交易適配器已實現低延遲增量對帳。
2. **合法減倉優先於部分增倉門檻，已存在。** `risk.evaluate` 在判斷 RUN／HEALTHY、日初基準與曝險上限之前處理減倉；但仍要求新鮮且核實的部位、合法數量與無衝突減倉。普通路徑遇 UNKNOWN 不會自動取得減倉許可。這不等於任何對帳失敗時都能下平倉單。
3. **S9／S10 已是獨立 local-sim 帳務能力。** 尚未接交易、風控或 funding 分攤，不能把「移到背景」當成現成的實盤解阻功能。Lot 費用歸因延後，不代表執行層的成交終態、帳戶權益或外部資金流可以不明。
4. **未使用分類的目錄覆蓋率，已不阻擋。** 2026-09-23 政策與 `reconciliation_gate._day_blockers` 一致；實際 bills 出現 unknown／forbidden、來源不完整仍阻擋。舊 gate 文件還保留相反敘述，本輪已修正。
5. **評估時真正需要重新選擇的是日初權益政策。** 舊 `risk.observe` 首次／新日缺少 basis 會記下 `basis_blocked_day`，同日後續補入仍拒絕。這對非全天開機的使用者有明顯限制；後續已依 R1 改為首次合格觀測，不再保證完整台北日的日損基準。
6. **Q1 不是所有 Demo／Live 的通用條件。** 現行 Q1 只允許 dedicated Demo 的 bootstrap day，以完整零事件區間證明當下權益等於午夜權益；不能推廣成一般帳戶日初建立方式。

上述為來源核對，沒有實測操作耗時，也沒有本輪交易或測試通過的宣稱。Gemini 原文中返佣比例、稅務、跨市場規則與模型能力不在本次評估範圍。

## 2. 首個交易閉環的最小交付

建議交付順序是：設定專用帳戶與既有風控參數 → 自動唯讀確認 → 清楚顯示可執行動作 → 啟動已選策略 → 由 Supervisor 執行與核實回報 → 查看部位、權益、風險原因與必要紀錄。

- 首個整合驗證案例使用一個 Bot、一個合約、一個週期；這是驗證範圍，不新增「整個產品只能一個 Bot」的限制。現行單合約單 Bot 所有權政策保留。
- 研究／模擬仍可獨立使用，不必先通過交易帳戶對帳。交易的就緒狀態不能封鎖單純研究與既有資料閱讀。
- 既有 3.0x／50%、Soft／Hard 10%／20% 與 P6 預設 0% 的政策不因本輪評估改值；不增加一套「散戶模式」與「機構模式」分支。
- 首次可用交易不以多 Lot 分配、完整 funding 歸因、費用更正工作流、全市場研究、跨市場或桌面封裝完成為前提。已完成能力保留；不取消其他已交辦的並行工作。
- 一個工作包包含必要實作、自測與交接，再交指定角色獨驗；不重新拆成多輪 assessment／spec／確認／實作核准。真正的新金融政策仍須先定案。

## 3. 保留、延後、警告與阻擋清單

「原保證」指評估時要求或已有能力；尚未接交易的能力，不寫成已提供的保證。表中必要測試為驗收要求；R1 後續實際自測範圍見第 8 節，不代表所有建議皆已實作。

| 項目／處理 | 原保證 | 精簡後保證或產品行為 | 可能漏判／不涵蓋 | 必要驗證 |
| --- | --- | --- | --- | --- |
| Decimal、固定 tag、單一 writer／交易出口：保留 | 金融計算與責任入口一致 | 沿用，不新增第二帳本或交易通道 | 普通 Worker 不是惡意程式安全沙箱 | 受影響時驗算小額費用、最小張數；一般與緊急路徑 tag 一致 |
| 意圖接受、送出前的兩次風控：保留 | 排隊期間新風險能阻止尚未送出的單 | 重用裁決邏輯，仍檢查當時 epoch、期限、部位與保留額度 | 已進 transport 的單不能宣稱撤回 | 意圖接受後插入 Kill／過期／部位改變，送出必須拒絕 |

| Lot 手續費歸因與進階報表：延後；缺項顯示警告 | S9／S10 僅 local-sim；不提供實盤風控輸入保證 | 首個交易流程不依賴 Lot 報表完整；未知損益明示，不展示為零或精確值 | 若連當前權益、成交終態或外部流都不明，不能只改成報表警告 | 只缺 Lot 歸因時不新增交易 gate；缺成交／權益證據時仍阻擋相應動作 |
| P6 交易所災難停損：維持可選 | 0% 不啟用；啟用後須核對完整保護責任 | 未啟用不冒充異常；啟用後失敗禁增倉，告知具體原因 | 未啟用不提供主機故障後的 P6 保護；存在一張 stop 不等於價格／數量正確 | 0% 無責任；啟用但方向／mark／價格／數量錯誤；停用待取消終態 |
| 日損／曝險異常下合法減倉：使用既有分流 | 核實部位、數量與衝突後允許降低曝險 | 顯示「可減倉、暫停增倉」；不把 NO_INCREASE 寫成全停機 | 新鮮度／部位證據不足或衝突減倉時仍不可放行 | Soft、被動超限、保證金不足；陳舊部位與第二張減倉必拒 |
| 暫時斷線／資料逾時：自動確認方向，非自動解鎖 | 失效資料不作新交易依據；已有 latch 不自解 | 在已授權來源與額度內，有界重取唯讀資料；合格後移除暫態原因 | 不能盲重送交易、延長舊證據有效期，不能自動 re-arm 或清 recovery_required | 斷線後恢復、持續失敗停止、恢復時已有 Soft／Hard latch |
| 重複訊息與內部檢查明細：合併呈現 | 完整保留原始原因與證據 | 同一事件顯示一個主因、影響動作與下一步；次要原因可展開 | 只保留第一個 blocker 可能隱藏另一個仍有效原因，因此不能刪底層原因 | 多原因併存；主因消失後另一原因仍禁增倉；日誌可追溯 |
| 多 Lot、精細成本分攤、進階研究、跨市場：不列首個交易前置 | 目前分階段交付，能力與授權各有邊界 | 使用已有單 Bot／合約路徑完成最小案例，不擴建通用框架 | 不保證同合約多 Bot、完整投資組合歸因或其他市場支援 | 最小閉環不必載入未接交易的 Lot／研究服務 |
| 風控基準：R1 local-sim 已實作、自測完成 | 舊精確台北午夜 E0；缺失當日不得重建 | 改為每日首個合格觀測開始的固定風控期間，詳見第 5 節 | 不涵蓋當日開始觀測前的損益與閾值穿越；尚未接 Demo／Live | 首啟、晚啟、跨日、同日重啟、入金、latch、邊界事件與持久化失敗 |

**沒有找到可直接刪除的整組金融檢查。** 可立即減少的是：錯誤的前置依賴、過時規範、重複操作與重複呈現。兩階段送單檢查、對帳前後 revision fence 分別處理不同時間的狀態變動；它們不是重播同一份歷史，不能以「檢查過兩次」為刪除理由。

## 4. 對使用者顯示動作，不暴露內部流程名稱

這是行為契約建議，未設計新畫面；下一包沿用現有介面，不要求使用者盲選視覺樣式。

| 狀態 | 增倉 | 減倉／清倉 | 其他操作與恢復 |
| --- | --- | --- | --- |
| 只有獨立報表歸因缺項，執行／帳戶證據完整 | 依原風控 | 依原風控 | 報表標示缺項，研究與查看可用 |
| Soft、被動曝險超限、缺日基準等增倉原因 | 禁止 | 僅既有條件證實為合法減倉時可用 | 顯示可做的動作；已鎖存原因仍人工 re-arm |
| P6 啟用但保護未確認 | 禁止該責任範圍新增曝險 | 沿用既有合法減倉條件 | 顯示實際保護狀態與確認時間，不能以目標價冒充已生效 |
| UNKNOWN、部位未核實、證據逾時／衝突 | 禁止受影響曝險 | 不保證可減倉；依現有 ordinary／Hard-Kill 路徑各自判斷 | 唯讀查詢；查詢與撤單也需既有狀態允許，不能提供無條件重試 |
| 陌生委託／部位、帳戶 equity 或資金流不明 | 帳戶級禁止增倉 | 只能處理可證明自有且合法的責任，不能接管陌生單 | 顯示來源與處理事項；不得說其他 Bot 一定能繼續交易 |
| Hard／手動 Kill 已鎖存 | 禁止 | 既有撤單、核實、reduceOnly 清倉流程 | 清倉完成不等於解鎖；原原因消失且條件合格才人工 re-arm |
| 儲存失效／recovery_required | 不承諾可交易 | 不承諾可下單清倉 | 顯示可靠的既存狀態及時間；不新增繞過 writer 的緊急通道 |

產品可將檢查收成一次「準備策略」流程，但 `reconciled`、策略啟用、交易授權仍是不同事實。唯讀對帳 PASS 不能直接變成 `trade_authorized=true`。

現行核心已有部分減倉分流，不代表正式 gate 與完整 UI 都已實現上述體驗。下一包只映射實際判定；若發現上層把所有 blocker 一律關閉減倉，須以具體呼叫鏈與案例提出修正，不能由前端自行推算「看起來能平倉」。

## 5. 已定案金融變更：R1 操作性風控基準

舊 exact-midnight E0 適合要求完整台北日可追溯損失的系統，但不能假設本機永遠在午夜連線，也不能把「午夜附近收到 balance」說成精確午夜證據。Q1 只解決極窄的 Demo 零事件首日。繼續要求這項精確保證，會使來源能力與離線使用方式成為首版難題。

使用者已核准 **R1：每日第一次取得合格帳戶證據時，建立該日固定的「本次風控期間基準」**。這是一項明確縮減保證的替代政策，不是缺證據時的靜默 fallback。

| 比較 | 舊 E0／E1 政策 | R1 已定案政策（local-sim 已實作） |
| --- | --- | --- |
| 基準含義 | 精確 Asia/Taipei 00:00 權益 | 當日首次合格觀測的權益與實際起算時間 |
| 上午首次使用 | 需合格午夜來源或符合適用範圍的 Q1；缺失後當日封鎖 | 可在合格觀測持久化後開始該日風控期間 |
| 同日重啟／中途斷線 | 使用既存基準；缺失不能換新 | 同樣沿用既存基準；不能因虧損、重啟、入金而重新起算 |
| 跨日 | 新日仍需精確午夜基準 | 先停增倉，取得並保存新日首個合格觀測後開始新期間 |
| 損失計算 | 當前權益減午夜 E0，再排除當日外部淨流 | 當前權益減期間基準，再排除起算後外部淨流；分母固定 |
| 對外名稱 | 完整台北日日損 | 必須顯示起算時間與「風控期間損益」，不能宣稱完整日日損 |
| 縮減的保證 | 仍受實際監控可用性限制 | 額外不涵蓋新期間開始前的當日損失；晚開機／跨日離線可能漏掉此前閾值穿越 |

R1 已定案的最小契約必須一起成立：

1. 帳戶、環境、台北日、實際起算時間、Decimal 權益、來源與證據引用綁定，經既有單 writer 保存後才可供 gate 使用。合格觀測仍受既有 freshness、完整性、ownership 與帳戶活動規則約束。
2. 同帳戶同日已有基準時只能讀取與冪等重放，不能替換。若本日狀態顯示基準曾建立或已有本日執行責任，但該基準損壞或遺失，禁止假裝首次安裝重建；正常跨日首次建立新日基準不屬於此例。
3. 首次／新日「資料尚未就緒」不再直接封死整天；在首次基準建立前禁止增倉，後續可重試收集。這明確取代該情境的 E1，並非以例外繞過它。
4. 資金流窗口從實際基準開始；若某筆入出金無法判定是否已含在基準權益，拒絕該組證據。不能直接改 timestamp 而沿用午夜 C_t，也不能將未知流量視為零。
5. Soft／Hard／manual Kill latch 跨日與重啟持續；新基準、恢復連線、反彈、入金或改門檻均不自動解除。既有基準之後的離線損益會反映於重連當下權益，但離線期間曾經越線又回升的過程，不能聲稱完整捕捉。
6. UI／報告使用新的期間名稱與起算時間；門檻數值可沿用既有設定，但使用者必須知道其衡量期間改變。不同期間的績效不可假裝整日可比。
7. 不承諾防止使用者刪光所有本機資料、重新安裝後重建預算；本機受信使用者不等於防竄改稽核系統。此類行為也不在本輪實作授權內。

**定案：採 R1；限定 local-sim 的基準與對帳實作包已完成開發自測，待獨驗。** 精確午夜 E0 不再作為 R1 強制前置，首次／新日資料暫缺不再封鎖整天；不再宣稱完整台北日日損。舊午夜來源與 Q1 的來源能力、歷史證據保留，不擴大其適用範圍。

R1 已同步固化至 `AGENTS.md`，影響 `risk`、baseline producer／provider、day-ledger／gate、持久化契約與報告語意。本次沿用既有風控 JSON，無 schema 變更或既有 DB 遷移；不新增「寬鬆／嚴格」雙模式。本機模擬已支援 R1，前端與 Demo／Live 未接入，不得宣稱完整產品流程已支援。

## 6. 後續最小驗收與工作順序

### UI 工作包：就緒狀態與操作指引

沿用現有 Bot／日誌元件，提供主因、影響範圍、允許動作、資料時間與下一步；完整原因可展開，不新增五張風控卡片。查詢刷新不得變成自動交易重試。先用隔離 fixture 驗證，再依既有串接工作包接真實後端讀取。

這一包可獨立進行，但不取代既有並行前端交辦；本次政策定案後優先完成下列 R1 後端包。若後端缺乏明確動作判定，沿用核心裁決做唯讀投影；不得由前端用三項快照或簡單 blocker 白名單自行授權。跨 Bot／帳戶範圍按真實責任資料呈現，不能為了顯示綠燈擅自局部放行。

### R1 local-sim 基準與對帳（已交付開發自測）

必要案例：

1. 上午首次合格觀測建立一次基準，保存前不放行；同日重啟不能刷新分母。
2. 同日先查詢失敗、後成功，可在無既存基準時建立；錯帳戶／錯日／舊資料不能建立。
3. 已有交易狀態但基準遺失、不同權益替換、寫入失敗／提交不明均不能產生成功狀態。
4. 跨午夜持倉或離線後回來，舊期間不能混用；新期間起算前禁增倉，舊 latch 保留。
5. 起算前後入出金、恰在邊界且歸屬不明、重複 bill；只排除可證明屬於期間的外部流。
6. 單純 Lot 報表缺費與真正成交終態缺漏分開驗證；後者不能藉 R1 繞過。
7. UNKNOWN 晚成交、foreign order、P6 異常、資料逾時仍保持原有阻擋。
8. 清倉與 ordinary 減倉各自保留其核實與衝突檢查，基準調整不擴大未知部位下的下單能力。
