## 資訊架構與工作區

頂層切換量化交易／Yaozi 情報；量化側欄為運行總覽、策略研究、執行工作台、帳戶與風控、事件紀錄。系統／Agent／服務版本放底部詳情，不占主流程。第一個樣稿展現前三個工作區與事件詳情；帳戶風控、情報與系統提供能力／缺口狀態，不以 mock 成功操作充數。

### 首頁：運行與異常

固定標示目前來源環境、資料時間及監看範圍；先看需要處理的事件，再看當前執行。

運行與異常                 監看預設／分割／放大／次要面板

### 策略研究

策略版本與資料選擇在左，中央為當次設定／結果／成交／候選，完整來源與假設置於詳情。策略製品、表單草稿、已保存 run 各有身分。

- 調整草稿只影響下一次提交，舊結果仍顯示自己的固定設定。
- 回測、Optuna 與 MCP 使用既有單一 ResearchService；Agent 任務出現在相同歷史，不建立另一份結果儲存。
- 正式目前只顯示 registry 的核可 SMA／固定合成資料，沒有任意 Python、CSV 上傳、URL 或自動核可入口。
- 搜尋候選可帶入新草稿／新回測，不能替換執行中的參數。跨版本比較、資料管理及策略生成工作流列後續範圍，不能展示成已完成能力。
- 完整 Decimal 以文字顯示；繪圖可使用衍生數值，但前端不重算帳務或風控。

### 執行工作台

選定一個 Bot／執行 run 後，讓使用者能追查：Closed Bar → 目標 → 已提交裁決 → 委託 → 成交。

- 頂部：來源環境、合約／週期、策略版本、資料時間、訊號進度、最後處理時間。
- 主欄：訊號目標與當時部位、裁決與原因、已記錄模擬成交；保持訊號與成交的差異。
- 次欄：資料可見性、未決責任／增倉限制的有效來源、完整製品／run 詳情。
- 本輪 R4 只從 status／manifest／events 取得快照；events 中訊號的 account 是該次決策前視圖，成交事件才是成交後視圖，不能一律稱現在帳戶。
- Worker 存活、資料新鮮、可以增倉、委託已終結與空倉分別顯示。停止 Worker 不等於平倉或釋放所有權。
- 首版只讀；不在樣稿放可成功執行的啟停、清倉、re-arm 或 Kill 控制。日後控制只由既有 Supervisor 受管契約處理。

## 首個正式接線的最小資料邊界（實作建議）

研究沿用現有 catalog、runs、task、result、report 與 submit API。執行只讀 adapter 從固定 local-sim 輸出根目錄讀已知 run_id 的 metadata／status／完整 event lines；拒絕任意 path／symlink，限制筆數與輸出，不建立 writer 或第二 Supervisor。不以 user request 指定 DB 或讀檔根目錄。

status 的原子換檔與 events 追加不是同一交易，讀取時要明示快照時間、來源計數與已完整讀到的事件序號；截斷末行不當成有效事件。計數不一致時顯示同步中，不能補造事件。running 不透過 UI adapter 對 live DB 宣告完整帳務／責任驗收；已完成 run 的正式完整驗收沿用 R4 verifier。

若需要新的 GET 路由，納入同一 FastAPI、同源與 localhost 邊界；正式 route 名稱／序列化契約在實作時固定。設計樣稿沒有新增此 API。本片不變更帳戶 freshness policy、交易授權或金融 gate。

資料表現須區分 loading、available、empty、partial、stale、unavailable、error；stale 表示 UI 觀測資料過期，不能自行解除 latch、釋放額度或決定清倉。實際增倉／責任狀態只取後端有效 snapshot；缺少即不可判定。
