# 研究線：真實歷史 K 線研究（工作包 C 方案）

更新：2026-11-04。使用者選定「研究線」並授權下方的採集範圍。本文件是方案與採集授權範圍，實作與實測結果見文末「實作紀錄」。

## 要解決的問題

研究 HTTP 目前只能用一份 96 根的合成資料，跑出來的績效沒有任何市場意義：
- 資料集寫死：`catos/research_catalog.py:21-22`（`DATASET_ID`、`DATA_PATH`），`validate_request` 遇到其他 id 一律 `unknown_dataset`（`:222`）。
- 合約規格寫死為 tick 0.01、lot 1（`research_catalog.py:245-248`），和真實 BTC-USDT-SWAP 不一定相同。
- 資金費固定為空（`research_catalog.py:248` 的 `()`），回測說明也寫「Synthetic only」。
- 單次回測上限 512 根（`MAX_BARS`，`:52`）。本機實測 Decimal 核心約每秒 4.5 萬根（5 萬根約 1.1 秒），所以這不是效能限制；真正的瓶頸是結果每根都輸出權益點，而輸出上限是 2 MB（`MAX_OUTPUT_BYTES`）。
- 現有抓取工具 `tools/fetch_okx_candles.py` 沒有資料來源紀錄、雜湊、缺口檢查與合約規格，而且每頁間隔 0.05 秒等於每秒 20 次，超過 OKX 公開的每 2 秒 20 次。

OKX 端點（第三方資料，實作時以實際回應核對）：
- `GET /api/v5/market/history-candles`：公開，每 IP 每 2 秒 20 次（[Hummingbot 連接器](https://github.com/hummingbot/hummingbot/pull/7022/files/d94ee1fde23adb3de1ed4b148e1d0e4eb9c3080d)）；回應含 `confirm`，只取已收盤（`confirm == "1"`）。

- `GET /api/v5/public/instruments`：公開，取 `ctVal`、`tickSz`、`lotSz`、`minSz`。

## 建議做法

**存法：CSV＋JSON manifest**，放在已被 git 忽略的 `data/okx/<instId>/<bar>/`。

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| **A. CSV＋manifest（建議）** | 沿用現有 `data_io.load_candles_csv` 與策略 manifest 的雜湊模式；只用標準函式庫；價格保持 Decimal 字串；不需新 DB schema | 檔案比 Parquet 大；3.5 萬列讀取不到 1 秒，不構成問題 |
| B. SQLite 表 | 符合 SQLite 底座，增量去重方便 | 要新 schema，依 AGENTS.md 需另行確認 |
| C. Parquet／feather | 讀寫快、檔案小 | 需要 pyarrow；預設浮點，違反 Decimal／TEXT 不變量 |

manifest 記錄：來源端點、`instId`、`bar`、起訖時間、列數、CSV 的 sha256、抓取時間、缺口檢查結果，以及當時的合約規格快照與資金費檔案的 sha256。研究端比照策略登錄：只接受 manifest 登錄、雜湊相符的資料集，不符即拒絕（fail-closed）。

**第一個切片範圍：BTC-USDT-SWAP、15m、最近 90 天**（約 8,640 根）。90 天落在資金費歷史的可回溯範圍內，所以回測可以帶真實資金費，不必標「未計資金費」。

## 採集授權範圍（需要你同意）

- 只呼叫上面三個公開 GET 端點，不用金鑰、不碰帳戶端點、不下單。
- 合約與週期：BTC-USDT-SWAP、15m，最近 90 天。
- 請求量約 90 次 K 線＋數次資金費＋1 次合約規格；每次間隔至少 0.25 秒（低於兩個限速），總時間約 30 秒。
- 資料存在本機 `data/okx/`（git 忽略），不上傳；另一台機器需要時用同一個指令自己抓，manifest 雜湊可互相核對。
- 只在這份資料上跑單一合約的回測與優化，不做全市場歷史回測。

## 實作內容（授權後一個工作包完成）

1. 抓取：改寫 `tools/fetch_okx_candles.py`，修正限速、加入重試、去重、缺口檢查、合約規格與資金費抓取，並產生 manifest。
2. 資料集登錄：`research_catalog` 改從 manifest 讀資料集清單，載入前核對雜湊；合約規格與資金費改由 manifest 提供；保留現有合成資料集。
3. 上限：`MAX_BARS` 依實測放寬（例如 2 萬根）；權益曲線在輸出時降採樣，避免超過 2 MB，績效數字仍用全部 K 線計算。
4. 前端：回測與優化頁加資料集選擇，並顯示資料說明（來源、區間、是否含資金費）。
5. 測試：抓取用離線假回應做單元測試（分頁、未收盤過濾、缺口、限速、重試）；manifest 雜湊不符要拒絕；整合測試涵蓋選擇資料集。
6. 驗收：完成後交另一個 Claude 會話獨立驗收。

## 不涵蓋與模型假設

- 仍是本根收盤決策、下一根開盤加滑價成交；沒有訂單簿、沒有保證金與強平模型，回測結果不代表實盤可得績效。
- 不做 1m 資料、多合約、多策略、策略上傳。
- OKX 的 `limit`、`after` 分頁語義與資金費回溯深度，要在第一次抓取時以實際回應核對，和文件不符就停止並回報。

## 實作紀錄（2026-11-04，分支 `feat/research-real-data`）

採集（依授權實際執行一次）：`tools/fetch_okx_candles.py --inst-id BTC-USDT-SWAP --bar 15m --days 90`，共 91 次請求。結果是資料集 `okx-btc-usdt-swap-15m-20260806-20261104`：區間 [2026-08-06 04:00, 2026-11-04 04:00) UTC，8,640 根、無缺口，資金費 270 筆、每 8 小時一次、涵蓋完整。分頁行為與預期一致（`after` 回傳更舊的資料、由新到舊、每頁最多 100 筆）。合約規格為 ctVal 0.01 BTC、tickSz 0.1、lotSz 0.01、minSz 0.01，和合成資料（tick 0.01、lot 1）不同。這 270 筆的 `realizedRate` 與 `fundingRate` 完全相同。

程式：
- `catos/research_datasets.py`：manifest 的唯一寫入者（`write_dataset`，拒絕缺口、資金費不完整或間隔不規則，以及覆寫）與驗證者（`load_manifest`，重算每個檔案的雜湊，並核對合約規格與 `instrument.json` 一致）。
- `catos/research_catalog.py`：`datasets()`、`resolve_dataset()`；`provenance(dataset_id)` 預設仍是合成資料，所以本機模擬路徑不變；合約、週期與資金費都由資料集提供；`MAX_BARS` 512 → 20,000。權益與回撤曲線超過 2,000 點時，每段保留回撤最深的一點，並在 payload 標明 `curve_sampling`；績效數字仍以全部 K 線計算。
- 研究服務、優化與驗證工作改用請求裡的資料集計算與核對來源。
- 前端：回測與優化頁加上資料集選擇（`components/catos/dataset-picker.tsx`）；績效數字改用 Decimal 格式化（原本直接顯示 50 位小數）；資金費說明改依資料集顯示；圖表座標軸取整、多日資料改用日期標籤。

### 採用的瘦身方案（結果 schema 升為 v2）

| 部分 | 做法 | 理由 |
| --- | --- | --- |
| 逐根環境標籤 | 改為七類環境的 K 線數（`label_counts`） | 實測改成區間（run-length）也有 3,540 段（lookback 4），不夠小；逐根標籤可由綁定的資料與規則重算 |
| 逐根分環境歸屬 | 只留各環境彙總與核對結果 | 彙總就是報告要呈現的內容；核對仍以全部 K 線計算 |
| 各窗 OOS 權益曲線 | 超過 1,000 ÷ 視窗數點才取樣，沿用 `sample_curve_indices`（保留起點與終點） | 與回測曲線取樣同一方法；合成資料不會觸發 |
| 來源快照 | `data/okx` 下的檔案只記路徑與 sha256 | 原本每份結果都內嵌 400 KB 的 K 線；資料已由 manifest 雜湊固定 |
| HTML 報表 | 改成摘要表 | 原本把整份 JSON 轉義後塞進報表，比結果本身還大 |
| 成交、資金費、訓練格點 | 不動 | 是 OOS 結果的證據；最壞情況量過仍在上限內 |

合成資料的結果除了去掉 `labels`、`intervals` 並加上 `label_counts`、`omitted_detail` 外，欄位與數值和 v1 完全相同（有測試逐欄核對）。欄位說明見 [驗證 API 契約](research-validation-api.md) 的「v2 輸出」。

另外加了送出前的計算量檢查：`windows × (候選數 × (warmup + train) + warmup + test)` 不得超過 250,000。實測有合法請求會超過 30 秒逾時（8 窗 × 11 候選 × 8,000 根訓練，程序內 36.7 秒）；同一台筆電每秒約 1.9～5.4 萬根（隨當下負載變動），以最慢的速度算，250,000 約 13 秒。

環境分類器的成本不在這個公式裡：每根 K 線都要加總整個回看窗，共約 (K 線數 − 回看根數) × 回看根數 步，本機每秒約 240 萬步。獨立驗收發現回看根數設到資料長度的一半（4,320）時，光分類就要 8 秒多（驗收觀察 O1）。所以回看根數上限改為 512（工作包 C 放寬 `MAX_BARS` 之前的實際上限是 511），8,640 根上分類最多約 1.8 秒，換成 20,000 根的資料集也只有約 1,000 萬步。最慢的合法請求（計算量邊緣加回看 512）以研究服務實測 8.29 秒。

### 規則

每根收盤決策、下一根開盤加滑價成交，固定張數，淨部位多空（`catos/research_donchian.py`）：

- 進場通道是前 `entry_bars` 根（不含正在決策的這一根）的最高價與最低價；收盤高於最高價做多、低於最低價做空，反向部位直接反手。
- 出場通道是前 `exit_bars` 根的最低價（多單）或最高價（空單）；收盤跌破就平多、突破就平空。
- 其餘情況維持部位。進場判斷先於出場：同一根收盤同時穿過出場與進場通道時直接反手。`exit_bars` 必須小於 `entry_bars`，所以出場通道比進場通道貼近價格，價格逐步反轉時會先平倉；預熱至少 `entry_bars` 根，且要留下可評估的 K 線。
- 通道用單調佇列維護，每根 O(1)，只做 Decimal 比大小，沒有任何算術捨入。

### 實作

- 研究端改成固定白名單兩個策略（`catos/research_catalog.py` 的 `STRATEGIES`）：各自釘住 id、version、entry、sha256、來源檔、manifest 與參數範圍。回測、優化、滾動驗證都依 `strategy_id` 驗證參數並載入對應策略；不是通用插件框架。

### 資金費缺口（B 的前提）

OKX `funding-rate-history` 只回溯約 3 個月（第三方實測，[athenum 部落格](https://athenum.mataroa.blog/blog/how-much-crypto-funding-rate-history-can-you-actually-get-four-venues-four-silent-limits/)；我們第一次抓取時 270 筆也符合），5 年資料約 98% 的期間沒有真實資金費。三種處理：

### 方案比較（查過的做法）

| 做法 | 回答的問題 | 成本 | 採用 |
| --- | --- | --- | --- |
| Deflated Sharpe Ratio（Bailey & López de Prado 2014） | 試了 N 組、報酬非常態時，最佳那組的 Sharpe 是否仍高於純運氣可得的最大值 | 低：只需各組的逐根報酬 | 是 |

- PBO 的判讀要保守（驗收觀察 O1 更正原說法）。原先寫的「0.10～0.27，選參過程本身沒有明顯偏差」只在 TPE 剛好抽到的 9 組上成立；完整格點的原範圍是 0.4571、聯集是 0.4286，代表選參過程有相當機率選到樣本外表現不佳的組合。另外 N 只有 9～21 組，λ 剛好為 0 的切法佔比也不小（原範圍 N=9 時 70 種切法有 11 種），PBO 粒度很粗。現在判讀文字在 N < 10 或 λ=0 佔比 ≥ 10% 時會加上這項提醒。
- 放寬範圍的 DSR 反而比較高，因為新增的參數組 Sharpe 彼此接近，試驗間變異數變小，純運氣的門檻跟著降低。這是 DSR 的已知性質，所以只看單次 DSR 不夠，要同時看合併 N 與 PBO。
- 這 5 窗的買進持有（+671.78）遠高於 Donchian；Donchian 的價值在空頭少虧（見上一輪 2025-09～2026-02 那窗），不在多頭多賺。
- 結論：Donchian 不放寬範圍，也還不適合當展示用的「會賺錢策略」。

### 已知限制與觀察

- 優化用 Optuna TPE，20 trials 在 12 點格點只評估到 9 組、15 點只評估到 10 組，有些格點沒被試到。格點小於 trials 時改用窮舉（GridSampler）會讓結果完整也更好重現，但會改變已驗收的優化行為，這一包沒有改，列為候選。
- DSR 的 N 只計本次執行；跨會話、跨工作包的累計試驗數目前沒有自動追蹤，前端只揭露同清單的其他優化任務數。
- Sharpe 以 close 估值的逐根權益計算，1 張相對本金曝險很小，Sharpe 不受曝險大小影響，但年化數字不是帳戶層級的 Sharpe。

### A. Donchian 多週期集成（`donchian-ensemble`，只做多）

- 9 個子模型，N = 5、10、20、30、60、90、150、250、360 日。
- 空手時，當日收盤高於前 N 日（不含當日）最高收盤就進場，停損設為含當日在內 N 日最高與最低收盤的中點。
- 持倉時，當日收盤低於前一日停損就出場；否則停損改為「前一日停損」與「當日中點」的較高者。
- 權重 = 持倉中子模型數 ÷ 9。
- 部位（`vol_scaling` = 1，主版本）：目標名目 = 權益 × 權重 × min(2, 25% ÷ σ)，σ 為最近 90 個日報酬的樣本標準差 × √365。
- 消融（`vol_scaling` = 0）：目標名目 = 權益 × 權重。
- 再平衡：目標為 0 而持倉不為 0 時一律出場；空手時目標大於 0 就進場；其餘情況只在目標與現有部位差距超過現有部位的 20% 時調整。
- `quantity` 是張數上限，量測用 1000，實際由 2 倍槓桿上限約束。

### B. 多週期時間序列動能（`tsmom-multi`，可多可空）

- 每日收盤計算 k = 30、91、365 日的報酬正負號（報酬為 0 時記 0），方向分數 = 三者平均。
- 主版本（`vol_scaling` = 1）：目標名目 = 權益 × 方向分數 × min(2, 25% ÷ σ)。σ² 用日報酬平方的指數加權平均（質心 60 日，λ = 60/61），以前 60 個日報酬的樣本變異數起始，年化乘 365。
- 消融（`vol_scaling` = 0）：目標名目 = 權益 × 方向分數。
- 再平衡規則、`quantity` 上限同 A。

### C. DCM 日線版（`dcm-daily`，可多可空，固定張數）

- 點位用前一個完整 UTC 日的 H、L、C：
  - DC = (H+L+C)/3
  - TC = (9H+9L+10C)/28
  - DH = TC + 0.8065 × (H−L)
  - DL = TC − 0.8065 × (H−L)
  - 不使用台股 ±9.5% 夾值。
- `score_filter` = 0（指標原義，對應箭頭的 arrow_bias）：當日收盤 ≥ DH 就做多 `quantity` 張；收盤 < DL 就做空 `quantity` 張；其餘情況維持原部位。
- `score_filter` = 1（加評分濾網）：沿用原指標去掉 VWAP 的評分，分數範圍 15～85。
  - 評分 = 50 + 月線斜率分 + DCM 分。
  - 月線斜率分：20 日均線日變化率，≥3% 為 +15、≥1% 為 +10、>0 為 +5、≤-3% 為 -15、≤-1% 為 -10、<0 為 -5。
  - DCM 位置分：收盤 ≥ DH 為 +10、> DC 為 +5、≤ DL 為 -10、< DC 為 -5。
  - DCM 趨勢分：今日 DH、DL 都高於昨日為 +10，都低於昨日為 -10。
  - 做多觸發時分數要 ≥ 60 才進場，做空觸發時要 ≤ 40；反向觸發出現但分數不允許時改為空手。
- 量測用 `quantity` = 10 張（0.1 BTC）。

### 驗證強化（每個變體都做）

- 回測績效：淨損益、價格損益與成本拆解、成交筆數、每邊兩平成本、最大回撤、日報酬年化 Sharpe。
- 買進持有基準：A、B 用期初 1 倍名目（本金 ÷ 首根開盤 ÷ ctVal，向下取整）；C 用同張數。
- 逐年（UTC 曆年）淨損益與同期買進持有。
- 成本加倍壓力測試：手續費 0.001、滑價 4 bps。
- 延遲測試：每個目標晚一根才生效（第 t 根收盤決策、第 t+2 根開盤成交）。
- 區塊 bootstrap：日報酬、20 日區塊、2,000 次、seed 20261106，報告平均日報酬的 95% 信賴區間與不為正的比例。
- 多重試驗：6 個變體用 `search_report` 算 DSR 與 PBO；另外把同一份 4H 資料先前試過的 SMA 7 組與 Donchian 16 組加進 N（合計 29），重算一次 DSR 當較保守的參考。

### 展示候選門檻（事前固定）

一個變體要同時滿足下列四項，才列為「展示候選」：
1. 成本加倍後淨損益仍為正。
2. 延遲一根後淨損益仍為正。
3. bootstrap 不為正的比例 ≤ 0.10。

只滿足 1～3 項的標「有跡象」，其餘標「不通過」。另外報告和買進持有的 Sharpe 與最大回撤對照；淨損益低於買進持有，不會讓變體不通過，但要明示。

  - bootstrap 平均日報酬為正的比例約 93.5%～95.5%，但 95% 信賴區間下限略低於 0。
  - 這和文獻方向一致，也和上一包 4H Donchian 的「有跡象」一致。
- **A、B 的價值在回撤，不在報酬**：
  - 4 年報酬 +58%～+133%，遠低於買進持有的 +272%。
  - 波動目標版最大回撤 16～17%，買進持有是 53%；Sharpe 0.85～0.91，略低於買進持有的 0.98。

- **A 與 B 相關 0.653**：同一類押注，同時展示兩個並不會分散。
- **DCM 日線版不通過**：
  - 價格損益接近 0 或為負，主要虧損來自成本。
  - 2025 年虧 3,070.66 和 4,238.22；最大回撤 52～61%，比持有同樣 10 張還深。

### 量測計畫（在任何短週期資料上跑策略之前固定）

策略規則依使用者 2026-10-11 的交易者校準（`docs/dcm-research-plan.md`「交易者校準」與第一例回饋），在 5m、15m、1H、4H 的已收盤 K 線上執行；本根收盤決策、下一根開盤成交（現有模型，taker 手續費 0.0005、滑價 2 bps、本金 10,000、固定 10 張 = 0.1 BTC）。DCM 點位與工作包 E 相同：用前一個完整 UTC 日的 H、L、C 算當日 DH／DC／DL，不夾值；第一個不完整日與之後一整天不交易（需要前一個完整日）。

**F1. DCM 假突破反轉（`dcm-fade`，可多可空）**
- 進場：
  - 做多：當日某根 K 線 low < DL 之後（含同一根），出現收盤 > DL 的 K 線。
  - 做空：當日某根 K 線 high > DH 之後（含同一根），出現收盤 < DH 的 K 線。
  - 每個 UTC 日每個方向最多進場一次；只在空手時進場；同一根同時符合多空時不進場。
- 失效停損：從跌破（突破）起到進場那根為止的最低 low（最高 high），收盤跌破（突破）就出場。這一條是 2026-10-11 研究的慣例，不是使用者原話，兩個變體共用。
- 出場有兩個變體，都來自使用者列的選項：
  - `exit_mode` = 0「對側點位」：多單收盤 ≥ 進場日 DH 出場，空單收盤 ≤ 進場日 DL 出場（點位凍結在進場日）。
  - `exit_mode` = 1「日線 DC」：持有到某天日線收盤跌破（多單）或站上（空單）當天的 DC。
- 失效停損與出場在同一根同時成立時，就是出場，只出一次。

**F2. DCM 突破後回踩（`dcm-pullback`，只做多，依使用者描述）**
- 發動：某 UTC 日收盤 ≥ 當日 DH。
- 用發動日的 H、L、C 算出凍結點位（也就是次日的點位）。
- 之後 `window_days` = 3 天內：K 線 low ≤ 凍結 DC 之後（含同一根），出現收盤 > 凍結 DC 的 K 線，就做多。每次發動最多進場一次。
- 出場：收盤 < 凍結 DL（失效）；或日線收盤 < 當天 DC。
- （2026-11-08 補記，程式自始如此，但量測前沒有寫進文件）持倉中（含剛決定進場的那一根）遇到的發動日不登記；新的發動會取代還沒用完的等待視窗，以最新的發動為準。獨立驗收照字面另寫「持倉中也登記發動」，四個週期都更虧（5m -1,143.91、15m -433.23、1H -2,221.51、4H -2,421.04），結論不變。要改這兩條規則就是新的事前登錄，N 要累計。
- 週成本、月成本需要成交量，資料沒有，不納入。

**F3. 對照組：既有 Donchian 通道突破（`donchian-breakout`）**
- 用相同時間長度的參數：進場通道 1 天、出場通道 6 小時。5m 為 288／72，15m 為 96／24，1H 為 24／6；4H 不跑。

**資料與評估**
- 每個週期各自用整份資料，預熱 3 天：5m 864 根、15m 288 根、1H 72 根、4H 18 根。
- 週期與資料：5m 6 個月、15m 1 年、1H 3 年、4H 5 年（既有）。
- 共 15 個變體：F1 兩個出場 × 4 週期 = 8，F2 × 4 週期 = 4，F3 × 3 週期 = 3。

**每個變體都報告**
- 淨損益、報酬、最大回撤、日報酬年化 Sharpe。
- 勝率、賺賠比、獲利因子、每筆期望值、最大連虧、平均持倉。
- 價格損益與成本、每邊兩平成本、同張數買進持有。
- 成本加倍、延遲一根、日報酬區塊 bootstrap（20 日區塊、2,000 次、seed 20261106）、逐年。

**展示候選門檻**（事前固定，同工作包 E）
1. 成本加倍後淨損益 > 0。
2. 延遲一根後淨損益 > 0。
3. bootstrap 不為正的比例 ≤ 0.10。
4. DSR ≥ 0.95。DSR 用同一份資料上各變體的 Sharpe 變異數，N 取全部 15 個變體。

只滿足 1～3 項的標「有跡象」。另外，在 taker 成本下虧損、但每邊兩平成本 > 2 bps 的變體，標成「改用限價單才可能救」，作為之後做限價單模擬的篩選依據；不代表已經可行。

### 判讀

- **沒有任何變體通過**，也沒有「有跡象」：15 個都虧，成本加倍更虧，DSR 接近 0。
- **勝率不高**：
  - 依使用者校準的 DCM 假突破反轉（F1），勝率只有 11.8%～36.8%。
  - F1 扣成本前的價格損益在每個週期都是負的：問題在訊號，不在成本，改用限價單也救不回來。
  - 「對側點位」出場的賺賠比 1.87～4.12（5m～1H 是 2.92～4.12，4H 是 1.87），形態是「少數大賺、多數小賠」，不是高勝率。
- **F2 回踩**：15m、1H 扣成本前接近打平（+57.48、+67.68），但每邊兩平只有 1.18、0.40 bps，低於 maker 費率，連限價單也不夠。
- **F3 短週期 Donchian**：5m、15m 扣成本前是正的（+538.65、+1,131.98），但每邊兩平只有 2.05、2.34 bps，剛好高於 maker 的 2 bps。用限價單理論上可能救，但沒有任何滑價餘裕，而且限價單有成交不到的問題。
- **多空分開看（只是描述，不是事前假設，不能據此選規則）**：F1 對側目標在 1H、4H 的多單淨損益為正（+508.94、+803.89），虧損幾乎都來自空單（-4,741.59、-4,744.86），和期間偏多頭一致。看完結果才把它改成只做多，就是過擬合；要測只能另外預先登錄，而且 N 要累計。
- **結論**：在現有成交模型（taker、收盤決策、下一根開盤成交）下，5m～4H 的這些規則對 BTC 都沒有優勢。
