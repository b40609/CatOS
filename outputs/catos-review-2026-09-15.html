02 · 按处理优先级排列的发现

以下 3 项代码问题位于额外研究入口 catos/cli.py / catos/optuna_study.py。项目在 docs/local-simulation-plan.md:11 已明确把它们排除在当时的已验收基线外；不能据此否定标准 research_cli.py 或 optimization.py 的历史验收。
高优先级 · 数据损坏

1. 额外 CLI 可直接覆盖输入 CSV 或已有报告

run_cli() 解析输入及输出路径后，没有拒绝同一路径，也没有检查输出是否已存在。K 线读入并完成回测后，直接用 write_text() 截断写入。

触发条件：对一份可成功回测的 CSV，将 --report 指向同一份 CSV，或指向已有文件。该入口不检查输出扩展名，因此会把原内容替换为 HTML。

最小修复：复用标准入口的路径检查与独占创建；补“输入=输出”“已有输出”“写入中断”测试，不需要重构研究核心。

代码：catos/cli.py:87–94,127–129。已有可复用实现：catos/research_cli.py:206–221,243–265。本轮仅静态确认，未执行覆盖操作。

高优先级 · 研究结果正确性

2. 允许自选 symbol，却始终使用同一套合约规格

两个额外入口接受 --symbol，但均固定每张标的数量 0.01、tick 0.1、lot / min 1。更换合约名称不会更换计算规格。

影响：当输入合约规格与硬编码不同、且 OHLC 恰好仍满足固定 tick 时，校验可能通过，但名义价值、手续费和盈亏按错误单位计算。Decimal 只能保证所用数值的十进位计算，不能纠正错误合约单位。

最小修复：沿用现有 JSON 配置，显式提供合约规格；若暂不支持配置，限制为明示的合成样例，不把固定值宣称为多合约通用默认。

代码：catos/cli.py:97–111,152；catos/optuna_study.py:103–116,194。传播路径：catos/research.py:264,278–289。无需查询或猜测当前交易所规格即可确认该接口缺口。

中优先级 · 统计精度

3. 夏普比率在求收益率前将权益转为 Float

compute_annualized_sharpe() 先对相邻权益调用 float()，再相减及计算收益率。大权益下的小额变化可能被抹平，并在标准差为零时返回 0.0。

触发示例：相邻 Decimal 权益为 10000000000000000 与 10000000000000001，二进制浮点无法保留这个差异。此为数值反例，不是真实账户数据。

最小修复：收益率、均值及方差保持 Decimal；明确零方差、非正权益和时间频率的统计语义，补大基数小变化测试。该问题影响额外脚本显示的 Sharpe，未发现其回流至账务或风控。

代码：catos/optuna_study.py:59–84,170–182。已验收优化控制器的转换边界另见 catos/optimization.py:102–110,162–177，不要混为一谈。

中优先级 · 交接与授权一致性

4. 当前状态和单次例外散落在互相冲突的文件中

  • README.md:3–7 仍称 I-b-4 待执行、I-b-3 待验证；WORK_PLAN.md:3–13 已记载采集与验收完成。
  • docs/demo-collection-handoff.md:5 仍称 config gate 未通过；同文件 65–73 已记载 gate 通过及剩余对账差异。
  • AGENTS.md:21 保留旧的指定来源与“Demo 子账户”单次例外；WORK_PLAN.md:7–9 和实际入口 catos/demo_collection.py:30,249–250 已反映更新后的来源与 Demo 主账户。

影响：后续开发者可能误判完成阶段、执行角色或沿用已消耗的单次授权。文档里的历史授权不是本轮重新采集权限。

最小修复：统一一个“当前状态”入口，旧记录保留日期并明确为历史；对齐单次主账户例外与正式交易子账户政策，不扩大例外、不自动重跑。

中优先级 · 测试接口错误

5. 新增模式查询测试访问不存在的 request.method

test_config_mode_read_is_one_demo_get_and_exposes_only_mode 在第 206 行断言 request.method，但 WireRequest 只有 host、target、headers、timeout_ms、max_body_bytes 字段，未定义 method。测试执行到这里会触发 AttributeError。

最小修复：在真实固定 GET 的 sender 边界验证 HTTP 方法，或明确调整请求契约；不要为了让测试通过而伪造方法字段。tests/test_demo_collection.py 当前静态已有 11 个测试，交接中的旧 9/9 记录不能代表这份代码现状。

证据：tests/test_demo_collection.py:197–213；catos/okx_http.py:90–99,188,452。这是静态可确定的接口不一致，并非本轮实际运行出的失败日志。

中优先级 · 审计来源准确性

6. 同 ID 冲突记录共享 observations 列表

同一订单 ID 的两条不同版本记录分别保留为 fact，但 observations[key] 始终复用同一列表。第二个版本追加来源时，第一个版本的 observations 也被改变，导致每个版本看起来均由两条来源支持。

影响：总体 conflicting_observation 仍会报警，未看到交易放行；但逐版本来源证据不准确。应按“身份＋内容版本”保存观察来源，另保留身份级冲突关系，并补“同 ID / 不同内容 / 不同来源”的测试。

代码：catos/account_report.py:210–229。现有冲突测试仅核对合计被抑制，未断言各版本来源隔离：tests/test_account_report.py:97–100。

待专项复现 · P5 / P6 交叉边界

7. 人工恢复未直接检查 pending / uncertain 保护责任

Journal.rearm() 检查 ownership 的条件单数量、未知单数及普通执行表，但没有调用 protection.obligations() 或检查保护状态。当首次保护建立请求未确认且 active 仍为空时，条件单数量可能仍为零；该保护的 pending / uncertain 不在普通执行表里。

候选场景：Soft 锁存原因已经消失、普通订单均终结且部位对账完成，同时首次保护建立待查询。此时 re-arm 可能清除账户锁存，却仍有保护 UNKNOWN。独立 protection.blocked() 仍阻止增仓，不能把该问题描述为已证明的交易绕过。

下一步：以该组合状态补 P5 × P6 合成测试，确认恢复条件应拒绝未决责任；不要把合法已确认保护单与未决保护操作混同，也不要自行扩大恢复政策。

证据：catos/journal.py:340–366,389–390；catos/protection.py:113–129,175–218；catos/execution.py:226–238。本项为跨状态待复现风险，不计为已执行测试确证缺陷。

03 · 当前阻断：采集完成，账户证据仍不足

最新采集记录明确列出 invalid_record:balance、missing_or_ambiguous:balance、mode_mismatch、归因未加载、P6 关联缺口，以及新鲜度、窗口与日初基准未核实。完整报告当时只在内存中，程序退出后没有保留。

本次不能确定余额失败的具体字段。解码器要求多个数值字段，但在报告边界把错误统一压缩成 invalid_record:<source>；模式不符也汇总成一个代码。仅凭摘要无法区分空值、不适用字段、格式问题或具体历史记录，不应猜测原因，更不能用零补值或放宽检查“消除错误”。

建议下一片：先增加不含数值、凭证和原始 ID 的结构化诊断（来源、字段名、错误类别、记录索引），用合成样本验证。若后续确需新账户证据，应另行确认采集及保存范围；本轮不执行。之后才核对适用账户模式、完成归因与对账证据，满足 J 的进入条件。

依据：docs/demo-collection-handoff.md:69–73；catos/account_report.py:67–82,198–203,235–245；catos/demo_collection.py:296–325,345–348。

04 · 值得保留的设计

  • 研究时序清晰：预热不决策，正式期只使用已收盘 K 线，下一根开盘撮合；未发现原指定研究核心的高置信具体缺陷。research.py:331–385
  • 精度边界明确：核心 Decimal context 隔离；标准优化器仅转换最终衍生评分。research.py:307–317、optimization.py:137–179
  • Worker 职责克制：严格 JSON、单在途事件、有界通讯及显式 ACK；普通进程隔离没有被夸大为 OS 安全沙箱。worker_host.py:138–206
  • 持久化与失败语义已有基础：SQLite WAL / FULL，以及显式 SUBMITTING / UNKNOWN 状态；这些是应继续验证的机制，不是已经完成真实交易保证。journal.py:163–166,237、execution.py:120–136,231–233
  • 阶段隔离正确：只读报告始终不给交易授权；当前缺数据时保持阻断，比绕过检查继续交易更符合项目约束。

05 · 建议处理顺序与验收

  1. 先修正新增测试接口并补交叉验证：模式查询测试核对真实 GET 边界；针对冲突来源隔离与 P5 × P6 未决保护恢复补最小合成测试。本轮没有执行这些测试。
  2. 限定额外入口的使用范围：修复覆盖风险与硬编码规格，或保持为未验收实验入口。专属测试只用临时文件与合成数据。
  3. 统一项目当前状态：更新首页及授权例外说明，保留历史验收记录；不把文档更新当成新的账户授权。
  4. 补足解码诊断及契约样本：验证缺值保持未知、模式错误定位准确、诊断不泄露数据。
  5. 再完成账户对账：补真实权益 / 保证金适配、归因、P6、来源新鲜度与日初证据；完成并另获 Demo 写入授权后才考虑 J。
